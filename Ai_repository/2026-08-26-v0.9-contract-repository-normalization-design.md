# CK V0.9 Contract Freeze and Repository Normalization Design

Date: 2026-08-26
Status: approved for implementation

## Objective

Release CalcKernel `0.9.0` as a coherent native compiler repository with a
frozen V0.9 source-language and backend ABI contract. Remove obsolete planning,
phase-history, migration, and tool-generated material; reorganize production
code, tests, examples, benchmarks, and durable documentation by responsibility;
and prove that structural changes preserve existing behavior before publishing
`v0.9.0`.

Work is performed directly on `main` in atomic commits. No feature branch or
additional worktree is used. The V0.9 tag is created only after local and
six-platform release-preview gates pass.

## Product Boundary

The shipped product remains:

- language name: CK / CalcKernel;
- source extension: `.ck`;
- compiler executable: `ckc`;
- Rust package and library crate: `calckernel`;
- native compiler outputs: MIR text, C/header, WAT/WASM, and LLVM IR/native
  artifacts.

This work changes repository organization and documentation authority. It does
not add language syntax, alter valid-program semantics, change diagnostics,
change CLI behavior, or change a documented backend ABI.

## V0.9 Compatibility Contract

All releases in the `0.9.x` line preserve the following observable surfaces.

### Source language

- Tokens, reserved words, primitive types, `ptr<T>`, `slice<T>`, structs,
  declarations, statements, expressions, precedence, type rules, evaluation
  order, and control-flow semantics remain compatible.
- Existing valid V0.9 source remains valid and retains its documented meaning.
- A `0.9.x` patch release may not add a reserved word because doing so could
  invalidate an existing identifier.

### Diagnostics

- Existing `CKxxxx` identifiers keep their category and meaning.
- A diagnostic identifier is never removed, reused, or assigned to a different
  condition within `0.9.x`.
- Wording, recovery quality, spans, and secondary context may improve without
  changing the identifier's meaning.

### CLI

- Existing commands, flags, aliases, default values, exit-code classes,
  mode combinations, and documented unsupported-mode behavior remain available.
- Unchecked overflow and unchecked bounds remain the defaults.
- C supports checked overflow and checked slice bounds. WASM and LLVM explicitly
  reject checked overflow and checked bounds.

### MIR v1

- MIR v1 types, instructions, places, terminators, and printed grammar are not
  removed or renamed in `0.9.x`.
- Printing remains deterministic.
- A correctness fix or optimizer change may alter concrete block order,
  temporary names, or instruction selection when the documented semantics are
  preserved. Exact output for a particular source file is a refactoring gate,
  not a permanent compatibility promise.

### C ABI

- Primitive type mappings, exported symbols, source struct field order, source
  void mapping, slice parameter flattening, and stored slice descriptors remain
  stable.
- Enabling checked overflow or checked bounds activates the module-wide status
  ABI. Non-void source returns use the final `ck_return` pointer; void source
  procedures do not.
- Status values remain `CK_OK=0`, `CK_ERR_OVERFLOW=1`,
  `CK_ERR_DIV_BY_ZERO=2`, `CK_ERR_NULL_POINTER=3`, and
  `CK_ERR_OUT_OF_BOUNDS=4`.
- Operand evaluation failures remain observable before the bounds guard that
  consumes their result. The checked non-void return pointer check remains the
  first body error.

### WASM ABI

- Export names, exported linear memory, scalar mappings, deterministic struct
  layout, pointer offsets, flattened slice parameters, stored slice descriptor
  layout, and internal slice multi-value returns remain stable.
- WASM remains unchecked-only in V0.9.

### LLVM ABI

- Exported function parameter and return shapes, void returns, and slice
  parameter flattening remain stable.
- LLVM textual IR is not a byte-for-byte compatibility surface.
- LLVM remains unchecked-only in V0.9.

### Explicit exclusions

The compatibility promise does not cover private Rust module paths, undocumented
Rust library details, byte-identical C/WAT/LLVM text, optimizer block and
temporary layout, performance measurements, machine code selected by host
toolchains, or behavior after invalid raw pointers, fabricated slice lengths,
misalignment, or expired caller-owned lifetimes.

Breaking changes require `0.10.0` plus an explicit migration record. `1.0` is a
later long-term stability commitment and is not implied by V0.9.

English durable documentation is organized by responsibility. The Simplified
Chinese tree mirrors every English document path below `docs/zh-CN/`. README
files are language-specific entry points into the same information architecture.

`src/lib.rs` preserves the existing flat public re-exports while implementation
files move behind private responsibility-based modules. `src/bin/ckc.rs` remains
thin; CLI parsing, commands, filesystem output, and external tool invocation live
in separate internal modules.

Integration-test drivers remain discoverable by Cargo and delegate to focused
files under responsibility directories. Shared process, fixture, compiler, and
temporary-path helpers live in `tests/support/`. Tests are moved and deduplicated;
assertions and coverage are not removed.

Examples are grouped into core language, applications, checked C, WASM, and LLVM.
Benchmark fixtures, cases, and baselines move under Cargo's `benches/` convention.
Every repository reference, CI command, oracle manifest, and durable document is
updated to the canonical path.

## Removed Material

The final V0.9 tree does not retain:

- `Ai_repository/` planning, adversarial review, readiness, or acceptance files;
- `docs/superpowers/` design and execution plans;
- historical `docs/releases/v0.7.0.md` and `v0.8.0.md` notes;
- legacy migration narratives whose only purpose is the TypeScript or IK-to-CK
  transition;
- phase-numbered descriptions presented as current specification;
- duplicated benchmark documentation;
- generated analysis metadata, local build output, or operating-system files.

Git history remains the historical record. Durable V0.9 docs describe only the
current product, its compatibility policy, and future work not yet implemented.

## Documentation Information Architecture

- `docs/reference/`: language, diagnostics, CLI, and MIR v1 specifications.
- `docs/abi/`: C, WASM, LLVM, and checked-status/mode contracts.
- `docs/compiler/`: current architecture and optimizer implementation guide.
- `docs/guides/`: getting started, backend selection, host interop, and
  performance usage.
- `docs/project/`: V0.9 compatibility policy, current roadmap, native release
  process, release checklist, and contribution/naming rules.
- `docs/zh-CN/`: exact directory and filename mirror of all English documents.

Normative documents use present tense. The roadmap contains only undelivered
work. Release notes describe V0.9 product changes, not internal phase history.

## Refactoring Method

1. Capture the clean `ce993eb` behavior baseline across official examples and
   O0-O3 MIR, C/header, WAT/WASM, and LLVM output.
2. Add repository-contract tests for version, current documentation authority,
   bilingual mirroring, links, mode matrix, status values, example paths, and
   absence of obsolete directories and historical wording.
3. Rewrite durable documentation and bump `Cargo.toml` plus `Cargo.lock` to
   `0.9.0`.
4. Split frontend, IR, optimizer, backend, and CLI files in mechanical commits.
   A structural commit may not intentionally modify algorithms or public output.
5. Reorganize tests, examples, and benchmark assets and update all consumers.
6. Remove obsolete material and strengthen ignore rules.
7. Run the complete local and release-preview gates before publishing.

Each responsibility group is committed separately. If a move exposes a real bug,
the reproduction and behavioral fix are isolated in their own commit rather than
hidden inside a structural diff.

## Verification Gates

The release candidate must pass:

```text
cargo fmt --check
cargo clippy --all-targets --all-features --locked -- -D warnings
CALCKERNEL_TS_ROOT=/Users/lynn/code/CalcKernel cargo test --locked
cargo build --release --locked
target/release/ckc --help
```

Additional gates cover all official examples, O0-O3 output baseline equality,
C/WASM/LLVM runtime agreement, C checked arithmetic and bounds behavior,
documentation mirrors and links, release version consistency, benchmark smoke,
and `git diff --check`.

Exact output equality is required across the repository-only refactor even where
the V0.9 public contract does not permanently promise byte identity. This proves
that the reorganization did not smuggle in semantic changes.

## Release Procedure

1. Finish all atomic commits directly on `main` and confirm a clean worktree.
2. Run the complete local gate.
3. Push `main` to `origin`.
4. Dispatch `.github/workflows/native-release.yml` on `main` with
   `publish=false`; wait for all six platform builds and smoke tests.
5. Create the annotated tag `v0.9.0` only after the preview succeeds, then push
   the tag.
6. The tag workflow creates the matching GitHub Release after successful builds
   and uploads six archives plus six SHA-256 files.
7. Verify the workflow, twelve assets, one downloaded checksum, and one unpacked
   binary smoke test.

The tag is immutable. A defect found after tag publication is corrected in
`v0.9.1`; the `v0.9.0` tag and published assets are never moved or overwritten.

## Repository Metadata

- Package version becomes `0.9.0`.
- `CHANGELOG.md` and `CHANGELOG.zh-CN.md` describe V0.9 user-visible
  capabilities and compatibility.
- A standard MIT `LICENSE` is added with copyright holder `luxine`.
- Cargo description is rewritten as the current native CK compiler rather than
  as a Rust rewrite.
- `AGENTS.md` is updated to describe the final durable-document structure and to
  prohibit committing temporary planning or generated analysis artifacts.

## Acceptance

The work is accepted only when the final repository matches the target
information architecture, contains no obsolete planning/history tree, exposes
one unambiguous V0.9 contract across all formal documents, preserves every
existing behavior gate, passes the native six-platform preview, publishes
`v0.9.0`, and verifies the GitHub Release artifacts.
